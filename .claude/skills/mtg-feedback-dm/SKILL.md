# MTG FB自動DMジョブ

Leo（小柴礼生）のGoogle Calendar上で**終了済みの対象MTG**を検知し、Google Drive上のGemini文字起こしから
**Leoが会議中に相手へ伝えたフィードバック（FB）だけ**を抽出・整理して、対応表で決められた相手に
**Slack DM（1MTG = 1メッセージ）**で送付する。

このスキルは**冪等**に設計されている。1時間おきに何度起動されても、既に処理済みのMTGは二度と送らない。
毎回まっさらなセッションから起動される前提なので、**状態はすべて自分宛DM（U02GDKKU5UH）のログ投稿から復元する**。

`mtg-memo-auto-post`（議事録の #p_mtg-memo-leo 投稿）とは独立したジョブ。同じ文字起こしを読むが、
お互いの投稿履歴には依存しない。

### タイトルの照合ルール

カレンダーのタイトルは表記ゆれする（スペースの有無、全角/半角、`[]`と`【】`、`/`と`／` 等）。
**タイトル全体の文字列一致はしない。** 空白・記号を除去し英数字を半角小文字に正規化したうえで、
次の条件で判定する：

- `mission進捗確認` を含み `kentaro` を含む → Kentaro Yamamoto
- `mission進捗確認` を含み `anna` を含む → Anna Kamada
- `よもやま` を含み `takuro` または `saito` を含む → Takuro Saito
- `よもやま` を含み `kazu` を含む → Kazuhiro Tamura
- `1on1` を含み `daigo` を含む → Daigo Hatano
- `performancedesign` を含む → Daigo Hatano
- `企画推進` を含む → Kazuhiro Tamura

どれにも該当しないMTGは**対象外**（何もしない）。複数条件に当たった場合は上から先勝ち。
上記に該当しても、**送付先本人がそのMTGの参加者（attendees）に入っていない回は対象外**にする
（代理出席・本人欠席の回にFBを送らないため）。

## 前提

- Google Calendar / Google Drive / Slack のMCPコネクタが必要。いずれか未接続なら、その旨を出力して終了する。
- タイムゾーンは常に **Asia/Tokyo (JST)**。コンテナ時刻はUTCなので、
  最初に `TZ=Asia/Tokyo date '+%Y-%m-%d %H:%M (%a)'` で今日の日付を確定してから始める。
- Gemini文字起こしはGoogle Meetが自動生成するGoogle Docs。**MTG終了直後には存在しない。生成まで概ね10〜20分かかる。**
- DMは自動送信する（下書きで止めない）。ただし**FBが1件も取れなかったMTGでは何も送らない**（後述）。

## ワークフロー

### Step 1: 処理済みMTGの把握（重複防止）

1. `slack_read_channel`（channel_id: `U02GDKKU5UH`＝自分宛DM, limit: 50）でログを読む。
2. 次の形式の行を持つ投稿から `会議名 / 日付 / 開始時刻` を抜き出し、「処理済みキー」の集合を作る：
   `:card_index: 【FB-DM ログ】<会議名> ｜ YYYY/MM/DD HH:MM ｜ <宛先名> ｜ <結果>`
   結果が `送付済` `FBなし` `文字起こしなし` のいずれでも処理済み扱い（無限リトライを防ぐ）。
3. 照合は `会議名 + 日付 + 開始時刻` で行う。会議名は記号・空白を除去して比較する（表記ゆれ対策）。
   自分宛DMには未返信ダイジェスト等の他ジョブの投稿も混在するので、`【FB-DM ログ】` を含む投稿だけを見る。

### Step 2: 対象MTGの抽出

1. `mcp__Google_Calendar__list_events` で **今日（JST 00:00〜現在時刻）** のイベントを取得する。
   **その日の最初の起動（現在時刻が10:00 JST以前）の場合のみ、前日00:00〜24:00も併せて取得する**
   （夜遅く終わったMTGの取りこぼし回収）。
2. 対応表の照合ルールに合致するイベントだけを残す。さらに以下を除外する：
   - 自分が辞退（declined）したイベント／中止されたイベント
   - 送付先本人が参加者に入っていない回
   - Step 1 の処理済みキーに合致するもの
3. **終了から20分以上経過している**MTGだけを残す（Gemini文字起こしの生成待ち）。
4. 残りが0件なら、**何も送らず・何も投稿せず静かに終了する**。

### Step 3: Gemini文字起こしの取得

取得方法は `mtg-memo-auto-post` スキルの Step 3 と同じ。要点：

- **最優先はカレンダーイベントの `attachments`。** `title` が「Gemini によるメモ」の添付から
  `fileUrl` の `<FILE_ID>` を抜き、`mcp__Google_Drive__read_file_content` で読む。
- **定例（`recurringEventId` 持ち）は過去回のメモが複数添付されている。** リストの並びで新しいものを選び、
  本文冒頭の日付が対象日と一致するか必ず確認する。一致しなければ次の候補を読む。
  **過去回の文字起こしでFBを作って送るのが本スキル最悪の事故。日付確認は絶対に省かない。**
- 添付が無ければ `mcp__Google_Drive__search_files` でタイトル検索にフォールバックする。
- 見つからない／実質空の場合：
  - **MTG終了から3時間以内** … 今回はスキップ（ログも送信もしない）。次回の起動で再挑戦される。
  - **MTG終了から3時間超** … 相手には何も送らず、自分宛DMに結果 `文字起こしなし` のログだけ投稿して、以後リトライしない。

#### 本文の読み方（FB抽出には「文字起こし」セクションが必要）

Gemini のドキュメントは `# メモ`（概要／次のステップ／詳細）と `# 文字起こし`（全発言）の2部構成。
議事録と違い、**FBは要約側にはほぼ残らない。Leoの生の発言が載っている「文字起こし」セクションを必ず読む。**
先に前半の要約を読んで会議の文脈を掴み、それから文字起こしを読むと精度が上がる。

長い会議は `read_file_content` の出力上限を超えて `{fileContent: string}` のJSONファイルに退避される。
その場合は Bash で文字起こし部分を取り出す：

```bash
python3 -c "
import json,re
c=json.load(open('<退避されたファイルパス>'))['fileContent']
i=c.find('文字起こし', c.find('### **詳細**'))   # 後半（全発言）の開始位置
t=c[i:] if i>0 else c
print(re.sub(r'\(\[[0-9:]+\]\([^)]*\)\)','',t))   # タイムスタンプリンクを除去して圧縮
"
```

それでも大きい場合は3〜4分割して順に読む。**途中で読むのをやめない**（終盤のクロージングで
FBがまとめて語られることが多い）。Leoの発言者名は「小柴 礼生」「Leo Koshiba」等。
Geminiは話者名・固有名詞をよく崩すので、文脈で判断する。

### Step 4: FBの抽出とDM文面の生成

文字起こしから、**Leoが送付先本人に向けて伝えたFBだけ**を抽出する。

**FBに含めるもの：**

- 称賛・ポジティブな評価（「〜が良かった」「〜は素晴らしい」「助かった」）
- 改善の指摘・期待（「〜はもっとこうするといい」「〜が気になる」「次は〜を意識して」）
- アドバイス・観点の提供（「〜という見方もある」「自分なら〜する」）

**FBに含めないもの：**

- 業務指示・タスク依頼（それはネクストアクションであってFBではない）
- 単なる情報共有・意思決定・議論の応酬
- **第三者（他の社員・候補者・エージェント等）への言及や人物評。** 1on1の文字起こしには
  他メンバーの話が必ず混ざる。**送付先本人以外に関する内容は、FBの文脈説明に最低限必要な場合を除き
  一切DMに載せない。**
- 評価・処遇・報酬の具体的な数字や、健康・私生活に関する話題

**品質基準（安易に送る方が、送らないより害が大きい）：**

- **実際にLeoが会議中に口にしたFBだけを書く。** 文字起こしに無いFBを創作しない。
  言っていないことを「言った体」で送るのは最悪の事故。
- 言い回しは自然な書き言葉に整えてよいが、**内容・強さ・ニュアンスを変えない**
  （口頭の軽い指摘を重い指摘に書き換えない。逆も同じ）。
- FBかどうか確信が持てない項目は**落とす**。落とした結果ゼロ件になったら**送らない**。
- 実質的なFBが1件も無いMTG（純粋な進捗確認・作業会など）は正常系。相手には何も送らず、
  自分宛DMに結果 `FBなし` のログだけ投稿する。

### Step 5: DM送信とログ投稿

#### 5-A. 本人へのDM

`mcp__Slack__slack_send_message`（channel_id: **送付先のuser_id**）で1MTGにつき1メッセージ送る。

（下記の `␠` は**全角スペース1個だけを置いた行**（U+3000 `　`）。実際にはその1文字だけを書く）

```
:mailbox_with_mail: **<会議名>** ｜ YYYY/MM/DD(曜) HH:MM-HH:MM のフィードバック
␠
<相手の呼び名>さん、お疲れさまでした！今日のMTGでお伝えしたFBを整理して送ります。
␠
**:+1: Good（良かった点・続けてほしいこと）**
　• <FB内容 1〜2行>
　• <FB内容 1〜2行>
␠
**:arrow_up: More（改善・期待）**
　• <FB内容 1〜2行>
␠
**:bulb: アドバイス・観点**
　• <FB内容 1〜2行>
␠
補足や「ニュアンスが違う」があれば気軽に返信してください :pray:
_（このDMはMTGの文字起こしからLeoのFB発言を自動で整理して送っています）_
```

書式のルール：

- **1行目のヘッダは重複判定の予備キーなので、形式を絶対に変えない。**
- 会議名はカレンダーのタイトルをそのまま使う（勝手に短縮・整形しない）。
- セクションは Good / More / アドバイス・観点 の3種。**該当項目が無いセクションは見出しごと省略する。**
  全体で3〜8項目程度、1メッセージ2000字以内を目安に簡潔に。
- 末尾の自動生成の注記行は必ず入れる（本人がAI整理と分かるようにする）。
- **Markdownのテーブル記法と `>` の引用ブロックは使わない**（Slackで表示が壊れる。実測済み）。
  ブロックの区切りは空行ではなく全角スペース（U+3000）1文字だけの行にする
  （半角スペースだけの行は送信時にトリムされて消える）。
- 送信直前に `slack_read_channel`（channel_id: 送付先user_id, limit: 20）でDM履歴を読み、
  同じ `会議名 + 日付 + 開始時刻` のヘッダを持つ送信済みメッセージが無いことを確認する
  （ログ投稿だけ失敗した回の二重送信を防ぐ最後の砦）。あればスキップしてログだけ投稿し直す。

#### 5-B. 自分宛DMへのログ（全ケース必須）

処理したMTGごとに、`mcp__Slack__slack_send_message`（channel_id: `U02GDKKU5UH`）で1行ログを投稿する：

```
:card_index: 【FB-DM ログ】<会議名> ｜ YYYY/MM/DD HH:MM ｜ <宛先名> ｜ <結果>
```

- `<結果>` は `送付済` / `FBなし` / `文字起こしなし` のいずれか。
- **この行が次回以降の重複防止キーになる。形式を絶対に変えない。**
- DM送付に成功したのにログ投稿が失敗した場合は、ログ投稿を1回リトライする。

### Step 6: 送信後の確認

- 送ったDMを `slack_read_channel`（limit: 1）で読み直し、ヘッダや本文の描画が崩れていないか確認する。
  崩れていたら修正版を送り直す（その場合、古い方への言及は不要）。
- ユーザーが対話的に起動した場合のみ、送付したMTG・宛先・件数を報告する。
  Routineからの自動起動時は、対象0件なら**完全に無言で終了**する（通知ノイズを出さない）。

## 失敗時の挙動

- 文字起こしが見つからない → Step 3 の3時間ルールに従う。エラー扱いにしない。
- DM送信が失敗 → 1回リトライ。それでも失敗したらそのMTGはログを残さずスキップ
  （次回の起動で自然に再試行される）。
- カレンダー取得が失敗 → リトライし、それでもダメならエラー内容を出力して終了する。誰にも何も送らない。
- **自信が持てないFB・中途半端な抽出は送らない。** 送ってしまうと処理済みになり二度と作り直されない。
  見送って次回に回す方が安全。

## 手動起動時の使い方

ユーザーが「今日の1on1のFBをDMして」「◯◯さんへのFB送って」と言った場合もこのスキルを使う。
その際は Step 2 の「終了から20分」制約を緩めてよい（ユーザーが明示的に指示しているため）が、
Step 1 の重複チェックと Step 5-A の送信直前チェックは**必ず**行う。
対応表に無いMTG・相手を指定された場合は、宛先のSlack user_idをユーザーに確認してから送る（推測で送らない）。
