# MTG議事録 自動投稿ジョブ

Leo（小柴礼生）のGoogle Calendar上で**終了済みのMTG**を検知し、Google Drive上のGemini文字起こしから
議事録を生成して、Slackのプライベートチャンネル `#p_mtg-memo-leo`（channel_id: `C0AHY4WBHDJ`）に
**1MTG = 1メッセージ**で投稿する。

このスキルは**冪等**に設計されている。1時間おきに何度起動されても、既に投稿済みのMTGは二度と投稿しない。
毎回まっさらなセッションから起動される前提なので、**状態はすべてSlackチャンネルの投稿履歴から復元する**。

## 前提

- Google Calendar / Google Drive / Slack のMCPコネクタが必要。いずれか未接続なら、その旨を出力して終了する。
- タイムゾーンは常に **Asia/Tokyo (JST)**。
- Gemini文字起こしはGoogle Meetが自動生成するGoogle Docs（通常「Meet Recordings」フォルダ、
  タイトルは `<会議名> - YYYY/MM/DD - メモ（Gemini 作成）` や `〜 - 文字起こし` 等）。
  **MTG終了直後には存在しない。生成まで概ね10〜20分かかる。**
- 投稿は自動送信（下書きで止めない）。対象は**全MTG**（1on1・評価系も含む）。プライベートチャンネルのため。

## ワークフロー

### Step 1: 投稿済みMTGの把握（重複防止）

1. `slack_read_channel`（channel_id: `C0AHY4WBHDJ`, limit: 50）で直近の投稿を読む。
2. 各投稿の**1行目のヘッダ**から `会議名 / 日付 / 開始時刻` を抽出し、「投稿済みキー」の集合を作る。
   ヘッダの形式は Step 5 で固定してある：
   `:clipboard: *<会議名>* ｜ YYYY/MM/DD(曜) HH:MM-HH:MM ｜ <参加者>`
3. `【文字起こしなし】` マーカー付きの投稿も**投稿済み扱い**にする（無限リトライを防ぐため）。

投稿済みキーの照合は `会議名 + 開始日時` の組で行う。照合時の注意：

- 会議名が微妙にブレる（絵文字・全角半角）場合があるので、記号と空白を除去して比較する。
- **過去のヘッダは旧形式（曜日・参加者なし、区切りが `〜`）のものが混在する。**
  ヘッダ全体を文字列一致させず、`会議名` と `YYYY/MM/DD` と最初の `HH:MM` だけを抜き出して突き合わせる。
- スレッド返信は投稿済み判定に使わない（親メッセージのヘッダだけを見る）。

### Step 2: 対象MTGの抽出

1. `mcp__Google_Calendar__list_events` で **今日（JST 00:00〜現在時刻）** のイベントを取得する。
   - **その日の最初の起動（現在時刻が10:00 JST以前）の場合のみ、前日00:00〜24:00も併せて取得する**
     （夜遅く終わったMTGの取りこぼし回収）。
2. 以下を除外する：
   - 終日イベント
   - 自分が辞退（declined）したイベント
   - 会議でない個人ブロック（タイトルが「調整不可」「作業」「移動」「ランチ」「昼食」「休憩」「予備」「ブロック」等のみ、
     または `attendees` が自分1人だけ／人間の参加者が自分だけ（会議室リソースは `resource: true` なので参加者に数えない）の予定）
   - `#p_mtg-memo-leo` に既に投稿済みのMTG（Step 1 の集合と突合）
3. **終了から20分以上経過している**MTGだけを残す。
   （まだ20分経っていないものはGemini文字起こしが未生成の可能性が高い。次回の起動に回す）
4. 残りが0件なら、**何も投稿せず静かに終了する**。Slackにも「対象なし」等のノイズは投稿しない。

### Step 3: Gemini文字起こしの取得

対象MTGごとに実行する：

#### 3-1. まずカレンダーの添付ファイルを見る（最優先・ほぼこれで足りる）

Step 2 で取得したイベントには、Gemini がメモを生成すると `attachments` が付く：

```json
"attachments": [{"fileUrl": "https://docs.google.com/document/d/<FILE_ID>/edit?usp=meet_tnfm_calendar",
                 "title": "Gemini によるメモ"}]
```

`title` が「Gemini によるメモ」の添付があれば、`fileUrl` から `<FILE_ID>` を抜き出して
`mcp__Google_Drive__read_file_content` に渡す。**Drive の名前検索より確実なので必ずこちらを先に使う。**
「Gemini によるメモ」の添付が無い＝まだ文字起こしが生成されていない、と判断してよい
（議事資料など別種の添付だけが付いていることがあるので、`title` で必ず判定する）。

#### 3-2. 添付が無い場合のフォールバック

1. `mcp__Google_Drive__search_files` で検索する。クエリの当て方：
   - `title contains '<会議名の特徴的な語>'` かつ `mimeType = 'application/vnd.google-apps.document'`
   - ヒットしなければ、会議名の別の部分文字列、日付（`YYYY/MM/DD`）、「メモ」「文字起こし」「Gemini」等で再検索する
   - 会議名に記号や絵文字が入っている場合は、英数字・かなの塊だけを抜き出して検索する
2. 候補が複数あれば、**ファイル名に含まれる日付とMTG開催日が一致するもの**を最優先し、
   次に更新日時が会議終了時刻に最も近いものを選ぶ。

#### 3-3. 本文の読み方（コンテキスト節約）

Gemini のドキュメントは `# メモ`（概要／次のステップ／詳細）と `# 文字起こし`（全発言）の2部構成。
**議事録は前半の「概要／次のステップ／詳細」だけで十分な品質になる。**
文字起こし全文は前半の10倍近い量があり、読む必要はほぼ無い（前半が欠けている、
または明らかに要点を取りこぼしている場合だけ該当箇所を参照する）。

長い会議のドキュメントは `read_file_content` の出力上限を超え、
`{fileContent: string}` のJSONファイルに退避される。その場合は Bash で前半だけ取り出す：

```bash
python3 -c "
import json,re
c=json.load(open('<退避されたファイルパス>'))['fileContent']
end=c.find('文字起こし', c.find('### **詳細**'))   # 後半（全発言）の開始位置
s=c[:end] if end>0 else c
print(re.sub(r'\(\[[0-9:]+\]\([^)]*\)\)','',s))   # タイムスタンプリンクを除去して圧縮
"
```

見出しリンクの除去だけで半分以下になる。それでも大きい場合は
`### **概要**`／`### **次のステップ**`／`### **詳細**` をセクション単位で分けて出力する。

#### 3-4. 見つからない場合

見つからない／中身が実質空（数百字未満で議論の実体がない）場合の扱い：
   - **MTG終了から3時間以内** … 今回はスキップする（投稿しない）。次回の起動で再挑戦される。
   - **MTG終了から3時間超** … Step 5-B の「文字起こしなし」通知を投稿して、以後リトライしない。

### Step 4: 議事録の生成

**話題（テーマ）を単位に構造化する。** 議論を時系列でだらだら書かず、
会議で扱われた論点を3〜6個のテーマに割り、テーマごとに「論点 → 結論 → アクション」を1ブロックにまとめる。
これは実運用で選ばれた形式（テーマ別ブロック型）で、**勝手に変えない**。

> 下記の議事メモを読み解き、Slackにそのまま貼り付け可能な議事録を生成してください。
>
> まず会議全体を2〜3文で要約し、続いて話題ごとのブロックを作ってください。
> 各ブロックは以下の3要素で構成します：
>
> 論点 … その話題で何が問題になり、誰がどう主張したか。背景・固有名詞・数値を残す
> 結論 … その話題がどう決着したか。決まっていなければ「継続検討」と書く
> アクション … 担当者｜タスク内容｜期限（期限が不明なら「期限未定」）
>
> 条件：
> - 挨拶や雑談など議題に直接関係ない発言は除外する
> - 表現は平易かつ簡潔に、Slackで読みやすいスタイルで
> - 論点は圧縮しすぎない。後から読んで「なぜそう決まったか」が分かる厚みを保つ

テーマの切り方：

- **カレンダーの `description`（アジェンダ）があればそれをテーマの下敷きにする。**
  無ければ Gemini の「詳細」セクションの見出しを束ねてテーマを作る。
- Gemini の詳細見出しは細かすぎることが多い（1会議で15個など）。**関連するものは束ねて3〜6ブロックに畳む。**
  逆に1ブロックが長くなりすぎたら分割する。
- 会議冒頭の「今日のアジェンダ確認」はテーマにしない。
- どのテーマにも属さない連絡事項は、最後に「その他」ブロックとしてまとめる。

品質基準：

- アクションの担当者は文字起こし中の発言から特定する。特定できなければ「担当未定」。推測で断定しない。
- 固有名詞（人名・社名・ツール名・案件名）と数値（金額・件数・日付・%）は落とさない。
- 「結論」＝合意・意思決定、「アクション」＝実行タスク。混同しない。
  結論は「〜する」で終わる決定文、アクションは「誰が・何を・いつまでに」。
- 明らかな誤変換の固有名詞（TERASS関連用語など）は文脈から正しい表記に直す。
  Gemini はカタカナの人名・社名をよく崩す（「小柴→コ葉／小島」「三澤→ミ沢」等）ので、
  カレンダーの `attendees` の氏名を正として表記を揃える。
- ブロック内に書くことが無い要素は、行ごと省略せず `なし` / `継続検討` と書く。
- **意思決定に関係しない個人的な話題は落とす。** 1on1や採用の会では、容姿・私生活・人物評の雑談が
  文字起こしに混ざる。判断の根拠になっていないものは書かない。
  候補者・社員の評価は、選考や処遇の判断に直結する範囲（経験・スキル・希望条件・懸念点）に絞り、
  事実ベースで簡潔に書く。憶測や揶揄はそのまま転記しない。

### Step 5: Slack投稿

`mcp__Slack__slack_send_message` で `C0AHY4WBHDJ` に **1MTGにつき1メッセージ**投稿する。
複数MTGをまとめない（スレッドが読みやすく、後から個別に参照できるため）。

#### 5-A. 通常の議事録

（下記の `␠` は**全角スペース1個だけを置いた行**（U+3000 `　`）。実際にはその1文字だけを書く）

```
:clipboard: **<会議名>** ｜ YYYY/MM/DD(曜) HH:MM-HH:MM ｜ <参加者>
␠
**:dart: 要約**
<会議全体の要約 2〜3文>
␠
**① <テーマ名>**
　論点｜<何が問題になり、誰がどう主張したか>
　結論｜<どう決着したか。未決なら「継続検討」>
　:arrow_right: <担当>｜<タスク内容>｜<期限>
␠
**② <テーマ名>**
　論点｜...
　結論｜...
　:arrow_right: なし
␠
**:bulb: Leoの宿題**
• <タスク内容>｜<期限>
```

書式のルール：

- **1行目のヘッダは重複判定のキーなので、形式を絶対に変えない。**
  `:clipboard: **<会議名>** ｜ YYYY/MM/DD(曜) HH:MM-HH:MM ｜ <参加者>`
  重複判定は「会議名＋日付＋開始時刻」で行うので、参加者部分は照合に使わない。
- 会議名はカレンダーのタイトルをそのまま使う（勝手に短縮・整形しない）。
- 参加者は `attendees` から会議室リソースを除いた人の名前（姓 or 名の通称）を ` / ` 区切りで並べる。
  5名を超える場合は `Misawa / Anna / ほか4名` のように省略する。
- 要約は `**:dart: 要約**` の見出し＋プレーンテキストで書く。ここだけ読めば会議の帰結が分かるようにする。
  **`>` の引用ブロックは使わない。** 引用行の次に全角スペースの行が来ると引用が終端せず、
  以降のメッセージ全体が引用に飲み込まれる（実測済み）。
- テーマ番号は `①②③…`。テーマ名は `**` で太字にする。
- `論点｜` `結論｜` `:arrow_right:` の各行の頭には**全角スペース1つ**（`　`）を入れて字下げする。
- **トピック（テーマブロック）の区切りは、空行ではなく「全角スペース1個だけの行」で改行する。**
  Slackは完全な空行を詰めてしまう（場合によっては行ごと消える）が、
  全角スペース `　`（U+3000）を1文字置いた行は文字として残るため、
  ブロック間が1行分しっかり空いて格段に読みやすくなる（Leoの運用Tips）。
  適用箇所はヘッダの下／要約の下／各テーマブロックの間／Leoの宿題の前の4種。
  ブロック内部（`論点`→`結論`→`:arrow_right:`）は詰めたままにする。
  **半角スペース（U+0020）だけの行は送信時にトリムされて消えるので使わない**（実測済み。
  半角で投稿したところ、区切りが空行に潰れたり行ごと消えたりして効果がゼロだった）。
- アクションが無いテーマは `:arrow_right: なし`。複数ある場合は `:arrow_right:` 行を並べる。
- 最後に **Leo自身のアクションだけ**を `:bulb: Leoの宿題` として再掲する。
  Leoのアクションが1件も無い場合はこのブロックごと省く。

分量：

- **1メッセージ4000字を目安**。超えそうなら論点の文を短くして調整する。
- 結論とアクションは何があっても削らない。削るのは論点の記述量だけ。

Slack描画上の制約（実測済み。守らないと表示が壊れる）：

- **Markdownのテーブル記法（`| a | b |`）は本文ごと消える。絶対に使わない。**
- `**太字**` は `*太字*` に変換されて正しく表示される。箇条書きは `•` を使う。
- `` `インラインコード` `` はタグ風に表示される。
- **`>` の引用ブロックは使わない**（全角スペース行と組み合わせるとメッセージ全体が引用化する）。
- 投稿後に必ず Step 6 で描画を確認する。

#### 5-B. 文字起こしが見つからなかった場合（終了から3時間超）

```
:clipboard: **<会議名>** ｜ YYYY/MM/DD(曜) HH:MM-HH:MM ｜ <参加者>

:warning: **【文字起こしなし】** Gemini文字起こしが見つからなかったため、議事録を生成できませんでした。
録画・文字起こしがONだったかご確認ください。手動でメモを共有いただければ議事録化できます。
```

`【文字起こしなし】` の文字列は、次回以降のリトライを止めるマーカーなので必ず含める。

### Step 6: 投稿後の確認

- 全対象MTGを投稿し終えたら、`slack_read_channel`（limit: 投稿件数）で自分の投稿を読み直し、
  ヘッダ行が崩れていないか・本文が欠けていないかを確認する。崩れていたら投稿し直す。
- ユーザーが対話的にこのスキルを起動した場合のみ、投稿した件数と会議名の一覧を返す。
  Routineからの自動起動時は、対象0件なら**完全に無言で終了**する（通知ノイズを出さない）。

## 失敗時の挙動

- Google Drive検索が0件 → Step 3-4 のルール（3時間ルール）に従う。エラー扱いにしない。
- Slack投稿が失敗 → 1回リトライする。それでも失敗したら、そのMTGはスキップして次のMTGに進む
  （投稿されていないので、次回の起動で自然に再試行される）。
- カレンダー取得が失敗 → リトライし、それでもダメならエラー内容を出力して終了する。Slackには何も投稿しない。
- **中途半端な議事録は投稿しない。** 投稿してしまうと重複判定で「投稿済み」になり、二度と作り直されないため。
  自信が持てないときは投稿を見送り、次回の起動に回す方が安全。

## 手動起動時の使い方

ユーザーが「今日の分まとめて投稿して」「◯◯MTGの議事録を投稿して」と言った場合も、このスキルを使う。
その際は Step 2-3 の「終了から20分」制約を緩めてよい（ユーザーが明示的に指示しているため）が、
Step 1 の重複チェックは**必ず**行う。
