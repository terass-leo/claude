# 未返信Slack デイリーダイジェスト（自動投稿）

前日にLeo宛に飛んできた**個別メンション**と**DM／グループDM**のうち、**Leoがまだ返信していないもの**を洗い出し、
**自分宛DM**（`channel_id: U02GDKKU5UH`）に1日1メッセージのダイジェストとして投稿する。

朝いちで「今日返すべきものはこれだけ」が5秒で分かる状態を作るのが目的。一覧の網羅ではなく、
**要対応／共有・報告／Cc・FYI の仕分け**と**放置日数の可視化**に価値がある。

このスキルは**冪等**に設計されている。毎回まっさらなセッションから起動される前提なので、
**状態はすべて自分宛DMの投稿履歴から復元する**（前回どこまで棚卸ししたか、前回の要対応が消化されたか）。

## 前提

- Slack MCPコネクタが必要。未接続ならその旨を出力して終了する（DMには何も投稿しない）。
- Leoのuser_id: `U02GDKKU5UH`。投稿先は自分宛DM（`slack_send_message` の `channel_id` に `U02GDKKU5UH` を渡す）。
  **他のチャンネルには絶対に投稿しない。** DM・プライベートチャンネル由来の機微情報を含むため。
- タイムゾーンは常に **Asia/Tokyo (JST)**。Slack検索の `on:` もワークスペースのTZ（JST）で解釈される。
- 検索は `slack_search_public_and_private` を使う（DM・プライベートチャンネルを含むため）。
  このジョブの存在自体がプライベート検索への同意とみなす。毎回の確認は不要。

## ワークフロー

### Step 1: 前回ダイジェストの復元（対象範囲の確定と繰越の把握）

1. `slack_read_channel`（channel_id: `U02GDKKU5UH`, limit: 20, response_format: `detailed`）で自分宛DMを読む。
2. `【` で始まり `未返信ダイジェスト】` を含む行を持つ**最新の投稿**を探す。これが前回ダイジェスト。
   ヘッダと対象範囲の形式は Step 5 で固定してある：

   ```
   【M/D(曜) 朝 未返信ダイジェスト】
   要対応 N件（うち繰越 X件）／ 共有・報告 M件 ／ Cc・FYI K件
   対象範囲: YYYY/MM/DD 00:00 〜 YYYY/MM/DD 23:59
   ```

3. **今日の日付のダイジェストが既にある場合は、何もせず終了する**（二重投稿の防止）。
   ユーザーが手動で「もう一度作り直して」と明示した場合のみ例外。
4. **今回の対象範囲**を決める：
   - 始点 = 前回ダイジェストの `対象範囲` の**終点の翌日 00:00**
   - 終点 = **前日 23:59**（起動日の前日。8時起動なので当日分は対象外）
   - 前回ダイジェストが見つからない、または始点が終点より後になる場合は **前日1日だけ**を対象にする。
   - **範囲は最大7日で打ち切る**（長期間空いた場合、それ以上遡らない）。打ち切ったら判定メモに明記する。
   - 例: 月曜8時起動で前回が金曜朝 → 対象は 金00:00〜日23:59 の3日間。
5. **繰越候補の抽出**: 前回ダイジェストの `■ 要対応` セクションに載っていた各項目の
   **Permalink・チャンネル・送信者・元の日時**を控える。これらは Step 3 で再判定して、
   まだ未返信なら今回も「繰越」として再掲する。
   直近5件のダイジェストまで遡って繰越候補を集めてよいが、**元メッセージが7日より古いものは繰越しない**
   （そこまで放置しているものはSlackの問題ではないため、判定メモに「7日超のため繰越終了」と一言書いて落とす）。

### Step 2: 対象メッセージの収集

対象範囲の**日付ごとに**、以下2種類の検索を行う。どちらも `pagination_info` に cursor があれば
**全件取得するまで**繰り返す。途中で打ち切らない。

共通パラメータ: sort: `timestamp`、sort_dir: `asc`、response_format: `detailed`、include_context: `false`、limit: 20

#### 2-A. 個別メンション（全チャンネル種別）

- query: `"<@U02GDKKU5UH>" on:YYYY-MM-DD -from:me`
- **メンション記法は必ずダブルクォートで囲む**（`"<@U02GDKKU5UH>"`）。
  クォートなしだと0件で返ってくることがある（実測済み）。
- `channel_types` は指定しない（デフォルトで public / private / mpim / im すべて）。

#### 2-B. メンションなしのDM・グループDM

- query: `on:YYYY-MM-DD -from:me`
- `channel_types`: `im,mpim`
- 修飾子だけのクエリでも動く（実測済み）。DMで直接飛んできた依頼はメンション記法を伴わないことが多く、
  2-A だけでは取りこぼす。**この検索を省略しない。**

#### 2-C. マージと一次フィルタ

- `(channel_id, Message_ts)` の組で重複を除去する（2-A と 2-B は重複する）。
- 各メッセージについて **Channel名 / Channel ID / 送信者（＋BOTか否か）/ 時刻(JST) / Message_ts /
  Permalink / 本文** を控える。
- **同一スレッド内で複数回メンションされている場合は1件に統合**し、最新のメンション時刻で判定・表示する。
- 除外する（判定メモに件数だけ書く）：
  - `@here` / `@channel` の一斉呼び出しのみで、個別メンションが無いもの
  - Leo自身の発言（`-from:me` で基本除外されるが、取りこぼしがあれば落とす）
  - 定期配信のbot通知で実務アクションを伴わないもの（Google Calendar の予定通知、リマインダー、
    本文が空のbot投稿など）
- **bot発でも実務アクションを要求しているものは落とさない。** 例: freee勤怠エラー通知（Slackbot / Zapier経由）、
  勤怠打刻くん、各種承認依頼bot。これらは Step 4 の `■ 要対応（Slack返信以外）` に回す。

### Step 3: 返信判定

Step 2 で残ったメッセージと、Step 1 の繰越候補の**両方**について判定する。

#### 3-A. チャンネル（public / private）のメッセージ

1. **スレッドrootの特定**: Permalink に `thread_ts=` があればその値がroot。なければ自身の `Message_ts` がroot。
2. `slack_read_thread`（channel_id + root ts、response_format: `detailed`）でスレッド全体を取得する。
3. **返信済み**: スレッド内に `U02GDKKU5UH` 発のメッセージがあり、その ts が**対象メッセージの ts より後**なら返信済み。
4. **リアクションのみ**: 返信は無いが、対象メッセージの reactions に `U02GDKKU5UH` が含まれる場合。
   返信済み扱いにはせず、`■ 共有・報告` 側に「リアクション済み」と注記して置く。
5. どちらでもなければ **未返信**。
6. スレッドが取得できない（権限・削除等）場合はスキップせず「判定不能」として要対応側に残し、判定メモに理由を書く。

#### 3-B. DM・グループDM

DMはスレッドを使わずチャンネル直下でやり取りすることが多い。

1. `slack_read_channel`（channel_id: そのDMのID, oldest: 対象メッセージの ts, limit: 100）で以降の履歴を読む。
2. `U02GDKKU5UH` 発のメッセージが1件でもあれば返信済み。
3. 対象メッセージが `thread_ts` を持つ場合は 3-A と同様にスレッドも確認する。
4. どちらにも無ければ未返信。

#### 3-C. 繰越の判定

- 繰越候補が返信済みになっていれば、今回は載せない（消化済み）。
  ただし判定メモに `前回の要対応 N件のうち X件は返信済み` と1行書く（消化状況が分かるように）。
- まだ未返信なら今回も `■ 要対応` に載せ、**元メッセージからの経過日数**を `[N日放置]` として明示する。

### Step 4: 仕分けと優先度づけ

未返信と判定したものを、以下の4つに仕分ける。**この4分類と順番を変えない。**

#### ■ 要対応（返信・意思決定が必要）

Leoが動かないと止まるもの。以下のいずれかに当たるもの：

- 質問・確認依頼（「〜で良いでしょうか」「ご教示ください」「認識で良いですか」）
- 意思決定待ち（方針の合意、A/Bの選択、承認、GOサイン）
- 期限が明示された依頼、または期限が近い依頼
- レビュー依頼（資料・契約・コメントの確認）

並び順は**放置時間の長い順**（古い順）。先頭に優先度マーカーを付ける：

| 状況 | マーカー |
|---|---|
| 期限が本日または明日に迫っている | `:alarm_clock: **M/D期限**` |
| 1日以上放置（繰越） | `:red_circle: **[N日放置]**` |
| 経営判断・契約・労務リスクに直結する最重要 | `★最優先` |

（この表はスキル内の対応表であって、**Slack投稿にテーブル記法は使わない**。Step 5 の注意参照）

#### ■ 共有・報告（返信不要の可能性）

報告・共有・完了連絡・進捗の記録など。Leoの返信が無くても前に進むもの。リアクション済みのものもここ。
1件1行で簡潔に。同じ人の同種の連絡は1行にまとめてよい。

#### ■ 要対応（Slack返信以外）

Slackで返すのではなく、別システムでの作業が必要なもの。bot通知はここに集約する。
例: freee勤怠エラー（打刻修正）、経費精算の差し戻し、各種承認待ち。
**「何をすればよいか」を1行で書く**（「本日中に打刻修正が必要」等）。

#### ■ Cc・FYI

宛先が別人で、Leoは併記されているだけのもの。**除外はせず**、まとめて数行に圧縮する
（誰から何の件、というレベル。個別の要旨は不要）。判断材料としてだけ残す。

#### 要旨の書き方（このダイジェストの品質を決める部分）

- 各項目の `要旨:` は **1〜3文**。「何を聞かれているか」「何を決めればよいか」が読んだだけで分かるように書く。
- **依頼の核心（Leoが返すべき論点）を太字にする。** 朝の走り読みで論点だけ拾えるようにするため。
- 固有名詞（人名・社名・案件名）と数値（金額・日付・件数）は落とさない。
- 既に他の人が回答している場合はそれも書く（例:「Kentaroさんは『OK』済み。**Leoの確認だけ未**」）。
- 返信の要否のヒントを添える（`（要回答）` `（要方針決定）` `（共有のみの可能性）`）。**要否は断定しない。**
- **DM・プライベートチャンネル由来の機微情報（個人の評価・処遇・労務個別案件・健康情報）は要旨レベルに留め、
  本文を転記しない。** 投稿先は自分宛DMだが、それでも「誰の何の件で判断待ちか」までで止める。
- 件数が多い日は `■ 要対応` を**最大15件**までにし、超過分は「他N件（判定メモ参照）」として
  チャンネル名と送信者だけ列挙する。要対応は削らず共有・報告側を圧縮するのが先。

### Step 5: 自分宛DMに投稿

`slack_send_message`（channel_id: `U02GDKKU5UH`）で**1日1メッセージ**投稿する。分割しない。

```
【M/D(曜) 朝 未返信ダイジェスト】
要対応 N件（うち繰越 X件）／ 共有・報告 M件 ／ Cc・FYI K件
対象範囲: YYYY/MM/DD 00:00 〜 YYYY/MM/DD 23:59

■ 要対応
1. :alarm_clock: **M/D期限** #<チャンネル名>｜<送信者>｜M/D HH:MM
要旨: <1〜3文。論点は太字>
→ [スレッドを開く](<Permalink>)
2. :red_circle: **[N日放置]** <Group DM または #チャンネル名>｜<送信者>｜M/D HH:MM
要旨: <...>
→ [スレッドを開く](<Permalink>)

■ 共有・報告（返信不要の可能性）
・#<チャンネル名>｜<送信者>｜HH:MM｜<要旨1行> → [開く](<Permalink>)

■ 要対応（Slack返信以外）
・**<件名>**: <何をすればよいか1行> → [開く](<Permalink>)

■ Cc・FYI
<誰から何の件、をまとめて2〜3行に圧縮>

■ 今回の判定メモ
・<返信済みと判定して除外したもの、繰越の消化状況、取りこぼしの可能性など>
```

書式のルール：

- **1行目のヘッダと3行目の `対象範囲:` 行は、次回起動時の状態復元キーなので形式を絶対に変えない。**
  `【M/D(曜) 朝 未返信ダイジェスト】` と `対象範囲: YYYY/MM/DD 00:00 〜 YYYY/MM/DD 23:59`。
- 2行目のサマリー行が結論。ここだけ読めば「今日返すべきものが何件あるか」が分かるようにする。
- セクション見出しは `■ 要対応` `■ 共有・報告（返信不要の可能性）` `■ 要対応（Slack返信以外）`
  `■ Cc・FYI` `■ 今回の判定メモ` の5つ。**空のセクションは行ごと省略する**（`なし` と書かない）。
- リンクは必ず `[スレッドを開く](URL)` の形式にする。**裸URLは貼らない。**
  Permalinkは検索結果のものをそのまま使う（enterprise環境のためドメイン形式が特殊。自前で組み立てない）。

Slack描画上の制約（実測済み。守らないと表示が壊れる）：

- **Markdownのテーブル記法（`| a | b |`）は本文ごと消える。絶対に使わない。**
- **`>` の引用ブロックは使わない。** 引用行の次に空行が来ると引用が終端せず、以降が引用に飲み込まれる。
- `**太字**` は `*太字*` に、`[text](url)` は `<url|text>` に自動変換されて正しく表示される。
- 箇条書きは `・` または `•` を使う。
- 1メッセージ4000字を目安にする。超えそうなら `■ Cc・FYI` と `■ 共有・報告` を圧縮する。
  **要対応の項目と要旨は削らない。**

### Step 6: 投稿後の確認

- `slack_read_channel`（channel_id: `U02GDKKU5UH`, limit: 1）で投稿を読み直し、ヘッダ・`対象範囲:` 行・
  リンクが崩れていないか確認する。崩れていたら修正版を投稿し直す（次回の状態復元が壊れるため必ず直す）。
- Routineからの自動起動時は、**投稿して静かに終了する**。ユーザーへの追加報告は不要。
- 対話起動時のみ、投稿内容の要点（要対応の件数と一番急ぐもの）を1〜2行で返す。

## 未返信ゼロの日

**投稿をスキップしない。** ヘッダと `対象範囲:` 行が無いと次回の状態復元ができないため、
必ず以下の3行だけを投稿する（`■` セクションは全部省略）。

```
【M/D(曜) 朝 未返信ダイジェスト】
:white_check_mark: 要対応 0件 ／ 共有・報告 M件 ／ Cc・FYI K件
対象範囲: YYYY/MM/DD 00:00 〜 YYYY/MM/DD 23:59
```

土日祝の翌朝など、対象範囲にメッセージが1件も無い日も同じ形式で投稿する。

## 失敗時の挙動

- Slack検索が0件 → 異常ではない。未返信ゼロとして扱う（上記の3行を投稿）。
- スレッド／DM履歴の取得が失敗 → そのメッセージは「判定不能」として要対応側に残し、判定メモに理由を書く。
  **取得できなかったから落とす、は禁止**（返信漏れの見逃しが最悪の失敗）。
- 検索自体が失敗 → 1回リトライし、それでもダメならDMには何も投稿せずエラー内容を出力して終了する
  （中途半端なダイジェストを投稿すると、次回の対象範囲がその日まで進んでしまい取りこぼす）。
- 投稿が失敗 → 1回リトライする。それでも失敗したら投稿を諦める（次回起動時に対象範囲が
  自動で伸びるので取りこぼしにはならない）。

## 品質基準

- **取りこぼしゼロを最優先。** ページネーションは必ず最後まで回す。件数が多くても省略しない。
- **返信済みの誤判定に注意。** スレッド外（チャンネル直下の別メッセージ）での返信は検出できない。
  判定メモに「スレッド外で返信済みのものは検出できていません」と毎回1行添える。
- **要対応を共有・報告に入れる誤りが一番痛い。** 迷ったら要対応側に置く（見なくてよいものが1件増えるだけ）。
- 対象範囲の日付以外のメッセージを混ぜない（繰越は例外。必ず `[N日放置]` を付けて区別する）。
- 憶測で「これは返信不要」と断定しない。判断はLeoに委ねる。
- **勝手に返信・下書きしない。** 依頼された場合のみ後続処理を行う。
