# freee人事労務 → Google スプレッドシート 組織図自動同期

freee人事労務に登録された **部門・役職・従業員の所属情報** を Google Apps Script（GAS）で毎日取得し、
スプレッドシートに「組織図（フラット表／ツリー）」「部門マスタ」「役職マスタ」「変更履歴」として自動反映する仕組み。

- 手作業ゼロで **freee が唯一の正（Single Source of Truth）** を維持できる
- 前回同期との差分（入社・退職・異動・役職変更・兼務の増減・雇用形態変更）を **変更履歴に自動蓄積**、任意で Slack 通知
- 出力はフラットな表なので、そこから `QUERY`/`FILTER`/ピボットで部門別人数・役職別人数・エージェント×本部の人員計画突合などに二次利用できる

---

## 1. 全体アーキテクチャ

```
freee人事労務 API ──(OAuth2 / 毎日06:00 JST)──▶ GAS (このプロジェクト) ──▶ Google スプレッドシート
   /groups          部門一覧                          │                        ├ 組織図_フラット   ← 1人1所属=1行（兼務は複数行）
   /positions       役職一覧                          │                        ├ 組織図_ツリー     ← 部門階層のインデント表示＋メンバー
   /employees       従業員一覧（ページング）           │                        ├ 部門マスタ        ← 階層・親子・直属/配下人数
   /employees/{id}/group_memberships  所属・役職      │                        ├ 役職マスタ        ← 役職別人数・該当者
   /employees/{id}  雇用形態・肩書き（任意）           │                        ├ 変更履歴          ← 差分を追記（Slack通知も可）
                                                      └──▶ Slack Webhook（任意）  └ _meta             ← 最終同期・件数・警告・エラー
```

| ファイル | 役割 |
|---|---|
| `Config.gs` | 設定値（会社ID・シート名・取得オプション・トリガー時刻） |
| `Auth.gs` | freee OAuth2（認可コード → トークン保存、6時間ごとの自動リフレッシュ、リフレッシュトークンのローテーション対応） |
| `FreeeApi.gs` | API呼び出し（リトライ・401時の再認証・limit/offsetページング） |
| `Normalize.gs` | APIレスポンスの正規化（フィールド名の揺れを吸収。純粋関数） |
| `Build.gs` | シート出力用の行データ構築（フラット／ツリー／マスタ。純粋関数） |
| `Diff.gs` | 前回結果との差分検出と Slack 用サマリー（純粋関数） |
| `Sheets.gs` | シート書き込み・読み戻し |
| `Notify.gs` | Slack Incoming Webhook 通知 |
| `Main.gs` | エントリポイント `syncOrgChart()` / トリガー設定 / メニュー |
| `test/run-tests.js` | 純粋関数の node テスト（`node test/run-tests.js`） |

## 2. セットアップ手順（初回のみ・所要15分）

### Step 1: freee 側でアプリを作成
1. [freee Developers](https://developer.freee.co.jp/) → **アプリ管理** → **新規作成**
2. アプリ種別: **人事労務API** を利用するアプリ（プライベートアプリで可）
3. 権限（スコープ）: **従業員の参照**・**部門の参照**・**役職の参照** を許可
4. **コールバックURL**: `urn:ietf:wg:oauth:2.0:oob`（認可コードを画面表示する方式。GASにWebアプリURLを持たせなくてよい）
5. 発行された **Client ID / Client Secret** を控える

### Step 2: スプレッドシートと GAS プロジェクトを作成
1. 出力先のスプレッドシートを新規作成（例: `【HR】組織図_freee連携`）
2. メニュー **拡張機能 → Apps Script** を開き、このフォルダ内の `.gs` ファイルをすべて貼り付ける（ファイル名も同じにすると読みやすい）
   - `appsscript.json` はプロジェクト設定で「マニフェストを表示」にチェックを入れてから上書き（タイムゾーン `Asia/Tokyo` と V8 が設定される）
   - clasp を使う場合は `clasp push` でまとめて反映可
3. **プロジェクトの設定 → スクリプトプロパティ** に以下を登録

| キー | 値 | 必須 |
|---|---|---|
| `FREEE_CLIENT_ID` | Step1 の Client ID | ✅ |
| `FREEE_CLIENT_SECRET` | Step1 の Client Secret | ✅ |
| `FREEE_COMPANY_ID` | 事業所ID（TERASS: `11460330`。未設定なら Config の既定値） | 任意 |
| `SLACK_WEBHOOK_URL` | 変更検知・失敗時の通知先 Incoming Webhook URL | 任意 |
| `SPREADSHEET_ID` | スタンドアロン運用時のみ（コンテナバインドなら不要） | 任意 |
| `DEBUG_RAW` | `true` にすると `_raw_debug` シートに API 生データのサンプルを出す（初回確認用） | 任意 |

### Step 3: freee 認可（1回だけ）
1. エディタで関数 `getAuthorizationUrl` を選んで **実行** → 実行ログに URL が出る
2. URL をブラウザで開き、**事業所（株式会社TERASS）を選択して許可** → 画面に **認可コード** が表示される
3. スクリプトプロパティに `FREEE_AUTH_CODE` = 認可コード を一時保存し、関数 `saveAuthCodeFromProperty` を実行（成功するとこのプロパティは自動削除される。認可コードは短時間で失効するので手早く）
4. `checkAuthStatus` を実行し `refresh_token_set: true` を確認

### Step 4: 初回同期と自動化
1. `syncOrgChart` を実行（初回は Google の権限承認ダイアログが出る → 許可）
2. スプレッドシートに 6 シートが生成されることを確認。`_meta` の「ステータス」「警告」を見る
3. `setupDailyTrigger` を実行 → **毎日 06:00 頃（JST）** に自動同期
4. 以降、スプレッドシートを開くと **「freee同期」メニュー** から手動同期・認証確認・トリガー再設定ができる

> **初回は必ず `DEBUG_RAW=true` で実行して `_raw_debug` を確認**することを推奨。freee API のフィールド名は
> `Normalize.gs` で複数候補を吸収しているが、想定外の形だった場合はここを見て `normalize*` の `pick_` の候補キーを1行足せば済む。

## 3. 出力シートの仕様

### 組織図_フラット（メイン）
1 従業員 × 1 所属 = 1 行。兼務者は複数行になり「所属順」「兼務（主／兼務）」で区別。
列: 従業員ID / 従業員番号 / 氏名 / メール / 雇用形態 / 肩書き / 入社日 / 退職日 / 在籍ステータス / 部門L1〜L6 / 所属部門 / 部門コード / 部門ID / 階層 / 役職 / 役職コード / 所属順 / 兼務 / 部門フルパス / 同期日時

- **在籍ステータス**: `在籍` / `入社予定`（入社日が未来） / `退職`（既定では出力しない。`INCLUDE_RETIRED` で切替）
- **部門L1〜L6**: 部門マスタの親子関係をルートからたどって展開（freee の `level` には依存しない）
- 二次利用例: `=COUNTIFS('組織図_フラット'!J:J,"本部",'組織図_フラット'!V:V,1)` で L1=本部の主所属人数

### 組織図_ツリー
部門をフルパス順に並べ、階層位置の L 列に部門名を置いたインデント表示。直属人数・配下合計人数・メンバー（氏名（役職）、※=兼務）を併記。経営会議の「現状組織図」の下敷きにそのまま使える。

### 部門マスタ／役職マスタ
- 部門: ID・コード・名称・階層・親部門・フルパス・直属人数・配下合計人数・主所属人数・直属メンバー
- 役職: ID・コード・名称・人数・該当者（人数の多い順）

### 変更履歴（追記型）
| 種別 | 検知条件 |
|---|---|
| 入社 | 前回に存在せず、入社日が同期日から `NEW_HIRE_WINDOW_DAYS`（既定45日）以内 |
| 入社（着任） | 在籍ステータスが `入社予定` → `在籍` に変化 |
| 新規検知 | 前回に存在せず、入社日が古い（freee側で後から登録された等） |
| 異動（主所属） | 主所属（所属順1）の部門フルパスが変化 |
| 役職変更 | 主所属の役職が変化 |
| 兼務追加／兼務解除 | 所属順2以降の（部門×役職）集合の増減 |
| 雇用形態変更 | 雇用形態が変化 |
| 氏名変更 | 表示名が変化 |
| 退職・除外 | 前回に存在し今回消えた（退職日が入っていれば備考に表示） |

初回同期では履歴を作らない（全員が「新規」になるのを防ぐ）。変更があれば Slack に要約を通知。

### _meta
最終同期日時、ステータス、件数、処理時間、警告、エラー内容。**運用監視はこのシートと Slack 通知だけ見ればよい。**

## 4. 設計上の判断と注意点

- **freee が正、シートは読み取り専用**: 出力シートは毎回全置換される。手入力の補足列が必要なら、別シートで `VLOOKUP(従業員ID, ...)` して持つこと（従業員IDは不変キー）。
- **主所属の定義**: freee の所属配列の先頭を主所属としている。freee 側の表示順と一致することを初回に目視確認する。
- **トークン運用**: アクセストークン 6 時間、リフレッシュトークンは使うたび入れ替わり・90 日未使用で失効。日次同期が回っていれば失効しない。長期停止後に `invalid_grant` が出たら Step 3 を再実行。
- **同時実行**: リフレッシュは `LockService` で排他。手動同期とトリガーが重なっても二重消費しない。
- **実行時間**: 約100名で 200 リクエスト前後 → 1〜2 分。GAS の 6 分制限に対し `TIME_BUDGET_MS`（4.5分）を超えると詳細取得（雇用形態）を省略し `_meta` に警告を出す。従業員が増えて厳しくなったら `FETCH_EMPLOYEE_DETAIL=false` にする。
- **ページング**: `/employees` は `limit`+`offset`（`page` は無視される。過去の勤怠ダッシュボード実装で実地確認済み）。`with_no_payroll_calculation=true` で給与計算対象外（役員・業務委託等）も取得。
- **freee API リファレンスへのアクセス**: 本コードは開発環境からリファレンスを参照できない状態で書いているため、レスポンスのキー名は複数候補で吸収している。初回の `_raw_debug` 確認で確定させること。

## 5. 拡張の方向性（必要になったら）

- **Google Workspace ディレクトリ / Slack プロフィールとの突合**（メールをキーに、部署名の不一致検出）
- **人員計画（PROJECTION 2026）との差分**: 部門マスタの「配下合計人数」を計画人数表と `VLOOKUP` して充足率を出す
- **月次スナップショット**: `組織図_フラット` を `YYYY-MM` シートとして月初に複製（`syncOrgChart` の末尾に 5 行追加で可能）
- **Looker Studio 接続**: フラット表をデータソースにして部門別・役職別・雇用形態別のダッシュボード化
